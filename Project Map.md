# Project Map

Silvershield is a Flask cybersecurity-training app. Users register, pass SMS two-factor login, take a pre-survey, practice scam detection in desktop, mobile, and phone role-play modules, then take a post-survey. Progress and difficulty live in SQLite. Scenario text is generated by Groq (`llama-3.1-8b-instant`). Speech uses gTTS. OTP uses Twilio Verify.

## How a user moves through the app

1. `GET /` — home page (`templates/homePage.html`)
2. `GET /account_creation` — register (`templates/accountCreation.html` + `static/auth.js`)
   - `POST /register` — creates the user, logs them in, sends them to the pre-survey
3. `GET /login` — login page (`templates/loginPage.html` + `static/auth.js`)
   - `POST /login` — checks password; seeded user `testuser` skips OTP; everyone else gets an SMS code
   - `POST /verify_otp` — checks the Twilio code
4. `GET/POST /pre_survey` — required before any module (`templates/survey.html`)
5. `GET /dashboard` — progress hub (`templates/dashboard.html` + `static/dashboard.js`)
6. Training modules (each simulation needs 5 logged attempts before that module counts as done):
   - `GET /module1` — desktop email + desktop browser (`templates/desktopPage.html`)
   - `GET /module2` — mobile email, SMS, call, web (`templates/MobilePage.html`)
   - `GET /phone_roleplay` — branching phone-scam role-play (`templates/phoneRoleplay.html`)
7. When all three modules are complete, `GET /dashboard` redirects to `GET/POST /post_survey`
8. After the post-survey, the dashboard stays available
9. `GET /logout` — clears the session, keeps the language choice

Difficulty is stored per user, per channel, on a 1–4 scale (easy, medium, hard, very hard). A correct answer raises that channel by 1 (capped at 4). A wrong answer resets it to 1.

Languages: English (`en`), Spanish (`es`), Chinese (`zh`). `GET /set_language/<lang>` stores the choice in the session and redirects back.

## Database tables (created by `database.init_database`)

### `users`

Account plus six difficulty columns:

- `difficulty_email_desktop`
- `difficulty_internet_desktop`
- `difficulty_email_mobile`
- `difficulty_sms_mobile`
- `difficulty_call_mobile`
- `difficulty_web_mobile`

A seeded account is always written: username `testuser`, password `SilverShieldTest!1`.

### `scenario_attempts`

One row per training answer: type, platform, choice, correct answer, timing, AI feedback, message text.

### `critical_indicators`

Clue strings the user is credited with when they answer correctly.

### `performance_summary`

Running totals per user and scenario type: attempts, correct count, success rate, average time, indicator count.

### `module_progress`

How many scenarios are done for a module key. Cap is 5 (`REQUIRED_ATTEMPTS_PER_SIMULATION`).

### `pre_survey` / `post_survey`

Summary fields plus a full `response_json` blob.

### `system_usability_survey`

SUS questions 1–10 and the computed SUS score (written from the post-survey).

### `phone_roleplay_sessions`

One call practice: scenario, difficulty, start/end, score, outcome.

### `phone_roleplay_events`

Each choice, dialogue load, restart, and completion inside a session.

### `phone_roleplay_results`

Attempt count, hints used, indicators, behavior pattern, feedback text.

### `module_assessment_assignments` / `enrollments` / `results` / `scores`

Older A/B pre-post quiz data. The live routes no longer show these quizzes.

### `user_consents`

Analytics consent from the pre-survey.

### `survey_question_assignments`

Which knowledge questions were picked for this user and phase.

### `survey_responses`

One row per answered survey question.

Indexes: attempts by user+time, indicators by attempt, module progress, assessment lookups.

## `database.py` — functions

`_column_names(cursor, table_name)`
Returns column names via `PRAGMA table_info`.

`_table_exists(cursor, table_name)`
True if that table is in `sqlite_master`.

`_migrate_scenario_attempts(cursor)`
Creates `scenario_attempts`, or rebuilds it if old columns `attempt_number` or `critical_indicators_identified` still exist. Adds `message` if missing.

`_ensure_test_user(cursor)`
Inserts or updates the seeded `testuser` account with a hashed password.

`init_database()`
Opens `silvershieldDatabase.db`, creates every table above, adds missing columns, backfills `module_assessment_scores` from results, creates indexes, commits, closes. Also runs when the file is executed directly, and `app.py` calls it on import.

## `user_login.py` — functions

`connecting_to_database()`
Opens `silvershieldDatabase.db` with `sqlite3.Row` so columns can be read by name.

`user_registration(username, password, email, phone, address)`
Hashes the password and inserts a `users` row. Returns `(True, "User Registration Successful")` or `(False, error message)` on duplicate username/phone/email.

`verifying_login(usernameOrEmail, password)`
Looks up by username or email and checks the hash. Returns `(True, phone, username)` or `(False, None, None)`.

## `TWOFA.py` — functions

`_get_twilio_client_and_service()`
Reads Twilio env vars and returns `(Client, verify service SID)`. Raises if any var is missing.

`send_otp(phone)`
Starts an SMS verification to that number.

`verify_otp(phone, code)`
Returns True only if Twilio status is `"approved"`.

## `metrics.py` — functions

`_connect()`
SQLite connection with a 10-second lock timeout.

`log_scenario_attempt(...)`
Inserts a `scenario_attempts` row (computes duration from `start_time` if needed). Inserts each clue in `indicators_found` into `critical_indicators`. Creates or updates `performance_summary` (attempts, correct count, success rate, rolling average duration, indicator total).

`log_critical_indicators(username, scenario_attempt_id, scenario_type, indicators_found)`
Inserts indicator rows for an existing attempt. The main logger already does this itself.

`update_module_progress(username, module_name, scenarios_completed=None)`
Increments completed count by 1, or sets an explicit count. Never goes above 5. Updates `last_accessed`.

`get_user_performance(username)`
Returns `{success, data: [{scenario_type, total_attempts, correct_attempts, success_rate, avg_duration_seconds, critical_indicators_found}]}`.

`get_module_progress(username)`
Returns `{success, modules: [{module_name, completed, total, completion_percentage, last_accessed}]}`.

`get_attempt_history(username, scenario_type=None, limit=20)`
Newest attempts, optionally filtered by type.

`get_survey_comparison(username)`
Pre vs post module-assessment scores, plus `pre_survey` and `post_survey` summaries and `confidence_change`.

`get_learning_metrics(username)`
Total time, attempt counts, overall success rate, total indicators, and the six current difficulty levels.

`load_survey_config()`

`"pre_survey"` or `"post_survey"`.

`_get_existing_assignments(cursor, username, phase)`
Rows already stored in `survey_question_assignments`.

`_ensure_section3_assignments(cursor, username, phase, section)`
For knowledge section S3, picks `questionSelectionCount` questions per subsection (currently 1). Post-survey avoids the question ids already used in that user's pre-survey for the same subsection. Does nothing if assignments already exist.

`ensure_phase_assignments(db_path, username, phase)`
Runs the S3 picker and commits.

`_decorate_question(question, inherited_scale=None, subsection=None)`
Copies a question, fills type, translated scale labels, text, options, required, `fieldName`, subsection id and topic.

`_assignment_id_set(...)`
Ordered question ids assigned to one subsection.

`build_survey_view_model(db_path, username, phase)`
The object `templates/survey.html` renders: title, description, sections, and consent on the pre-survey only. S3 shows only assigned questions. Other sections show every question.

`_translate_consent(consent)`
Translates prompt, details, and button labels.

`_iter_questions(sections)`
Yields every question, including ones nested in subsections.

`_coerce_answer(form_data, question)`
`multiChoice` uses `getlist`; everything else is a stripped string.

Mean of integer answers, or None.

## Survey content (`survey_config.json`)

### Consent

Required yes/no before survey and analytics collection.

### Pre-training sections

- **S1** Demographics and Technology Background (`D1` age, `D2` sex, `D3` education, `D4` home language, `D5` internet hours, `D6` devices)
- **S2** Technology Proficiency
- **S3** Cybersecurity Knowledge Test — 1 random question from each subsection: `PHISHING_EMAIL_1`, `VISHING`, `SOCIAL_ENGINEERING`, `PASSWORD_SECURITY`, `RED_FLAGS`, `PRIZE_SCAMS`, `ONLINE_SAFETY`, `IDENTITY_THEFT`, `SAFE_BROWSING`, `ACCOUNT_SECURITY`
- **S4** Cybersecurity Self-Efficacy (`SE1`–`SE6`)
- **S5** Behavioral Intention (`BI1`–`BI5`)

### Post-training sections

- **S3** Same knowledge subsections, but a different question than the one shown pre
- **S4** Self-efficacy again
- **S5** Behavioral intention again
- **S6** Technology Acceptance: `PU` perceived usefulness, `EU` ease of use, `HM` hedonic motivation
- **S7** Usability and Accessibility: SUS (10 items) and `AC` accessibility items

## `app.py` — scenario generators

All of these are POST, all call Groq, and all have hardcoded fallbacks.

`POST /generate-email` — `generate_email()`
Body `platform`: `"mobile"` or `"desktop"` (default desktop). Coin-flip scam vs legitimate. Reads that platform's email difficulty. Returns `{success, email: HTML, expected_label: "scam"|"not_scam"}`.

`POST /api/generate_sites` — `generate_sites()`
Desktop browser. Reads `difficulty_internet_desktop`.

Inner helpers:

- `infer_brand_details(search_query)` — brand name and legit domain from the query
- `safe_extract_json(raw_text)` — strip fences and `json.loads`
- `normalize_result(parsed, fallback)` — title, url, description, `site_type`, `is_sponsored`
- `generate_one(prompt_text, fallback)` — up to 2 Groq tries, else fallback

`mode "list"` (default): 5 shuffled results (sponsored legit, sponsored phishing, two legit, one phishing). `mode "open"`: HTML mock page for the clicked result. Phishing pages are training mockups with placeholder fields. Other modes: 400.

`POST /generate-sms` — `generate_sms()`
Coin-flip scam vs legitimate SMS. Reads `difficulty_sms_mobile`. Optional `theme` (default bank / package / delivery / login security). Returns `{success, difficulty, expected_label, sms: {number, text, time, clues}}`.

`POST /generate-call` — `generate_call()`
Coin-flip scam vs legitimate call transcript. Reads `difficulty_call_mobile`. Optional `theme` (default government agency or tech support). Returns `{success, difficulty, expected_label, call: {number, caller_name, transcript, clues}}`.

`POST /generate-web` — `generate_web()`
Mobile browser. Reads `difficulty_web_mobile`.

Inner helpers:

- `safe_extract_json(raw_text)`
- `normalize_item(item, fallback_type)` — title, url, snippet, `site_type`
- `build_fallback_items()` — 2 ads and 6 mixed legit/phishing results

`mode "open"`: HTML for the clicked result. `mode "search"` (default): `{ads, results, pagination, clues}`. Query defaults to `"bank account security tips"`.

## `app.py` — scoring

`POST /api/analyze` — `analyze_email()`
Desktop email scoring. If the body includes `"type"`, it forwards to `analyze_any()`. If `expected_label` is present, correctness is computed locally and Groq only writes the explanation and clues. Otherwise Groq decides correct/incorrect. Updates `difficulty_email_desktop`, logs scenario type `"email"` / platform `"desktop"`, updates module progress `"email_desktop"`. Returns `{success, feedback, difficulty_now}`.

`POST /api/analyze_website` — `analyze_website()`
Desktop site scoring. Ground truth is `site_type` from generation (phishing vs legit). Groq writes explanation and clues. Updates `difficulty_internet_desktop`. Logs scenario type `"internet"` / platform `"desktop"`, module progress `"internet_desktop"`.

`POST /api/analyze_any` — `analyze_any()`
Shared scorer for email, internet, sms, call, and web. Body: `type`, `user_choice` (`scam`/`not_scam`/`fake`/`real`), `message`, optional `platform`, `expected_label`, `time_spent_seconds`. Mobile email uses `difficulty_email_mobile`. Other types use the map in the function. Same pattern: `expected_label` makes scoring local; otherwise Groq judges. Logs scenario type `"{type}_{platform}"` and updates module progress with that same key. Returns `{success, feedback, difficulty_now}`.

`if __name__ == "__main__":`
Runs the dev server on `0.0.0.0`, `PORT` or 5000, debug off. Production uses `gunicorn app:app` (see `render.yaml`).

## Frontend organization notes

The frontend is organized by responsibility so a visual change can be made in the smallest relevant file:

- `style.css` contains shared foundation styles: reset rules, reusable colors, form controls, buttons, and the `.is-hidden` utility.
- Each page or simulation has its own CSS file. Templates should link to that file instead of adding a page-level `<style>` block.
- Reusable classes describe purpose rather than a one-time visual value. For example, `.dashboardContainer--compact`, `.btn--assessment`, and `.message-audio-control` replace hard-coded inline styles.
- JavaScript may reveal an element by assigning `element.style.display`; `.is-hidden` provides the initial hidden state without putting `style="display:none"` in the template.
- The only intentional inline styles are the two `--scale-count` values in `survey.html`. They are generated from the number of Likert-scale labels in the survey data, so they cannot be a fixed CSS value.

When editing the frontend, keep structure and translated text in `templates/`, behavior in `static/*.js`, and presentation in `static/*.css`. This makes it easier to review changes and reduces the chance that a styling change breaks a route or interaction.
